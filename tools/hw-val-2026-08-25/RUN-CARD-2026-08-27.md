### #734 -- the 09:46 boot named the fault

The per-endpoint ring fix was correct and is keeping. It was not the whole fault.
09:46 read `HID polls=27628 reports=0 errors=1` and `MOUSE polls=302314 reports=0
errors=1`, and the new diagnostic printed the two completion codes:

```
host-xhci: interrupt-IN transfer FAILED slot=3 ep=3 trb=0x141b7b000 cc=4 [#734]   keyboard
host-xhci: interrupt-IN transfer FAILED slot=4 ep=3 trb=0x141b7d000 cc=3 [#734]   mouse
```

cc=4 is a USB Transaction Error, cc=3 a Babble Detected. Both HALT the endpoint: the
controller stops running that ring and ignores its doorbell until Reset Endpoint and
Set TR Dequeue Pointer are issued. hype only cleared its own "armed" flag and rang
again, so from the first error onwards it armed into a dead endpoint. That is what
`errors` frozen at 1 while `polls` climbs past 300000 means -- not a device failing
over and over, but a device that got exactly one chance.

Three changes went in (commit `1919410`), one per fault:

1. an error completion now runs the Stop/Reset/Set-TR-Dequeue recovery #254 already
   built for the bulk path, then re-arms -- bounded at 8 consecutive recoveries per
   endpoint, reset by the next good report;
2. `SET_PROTOCOL(Boot)` at claim time. The boot SUBCLASS says the device *can* speak
   boot protocol; HID 1.11 7.2.6 says it powers up in REPORT protocol anyway, and hype
   parses nothing but boot reports;
3. the TRB is armed at the ENDPOINT's wMaxPacketSize, not the caller's 8-byte buffer.
   The mouse's endpoint is mps=64; a device sending more than the TRB asked for is a
   Babble, which is cc=3 exactly.

(2) and (3) each independently explain the mouse's cc=3. The keyboard's cc=4 is a
bus-level error one second into the boot and is explained by neither -- (1) is what
turns it into a question this boot can answer.
