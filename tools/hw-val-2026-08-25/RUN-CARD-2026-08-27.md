## The 11:23 boot answered the root-port question, and asked a better one

The keyboard on ctrl1 root port 5 -- `route=0x00000 ttslot=0`, a real root port --
reported: `host-hid: FIRST report received -- USB keyboard is live`. So the device is
fine and the hub path is implicated.

But the mouse, which had not moved, then failed with cc=4 where it had worked the boot
before. Exactly one variable changed for it: with the keyboard gone from the hub, the
mouse inherited **slot 3** instead of getting slot 4.

Slot 3 on ctrl2 is the id that `eba4:6579` takes first and gives back when the inventory
visitor releases it:

```
10:42  eba4 took slot 3, released -> keyboard inherited slot 3   cc=4, 0 reports
       mouse took a fresh slot 4                                 548 reports, 0 errors
11:23  eba4 took slot 3, released -> mouse    inherited slot 3   cc=4, 0 reports
       keyboard on ctrl1, fresh slot 2                           reports fine
```

Four device-instances, no exceptions: **every failing device sat on a recycled slot id,
every working one on a fresh id.** Same hub, same TT, same port, same endpoint, same
interval. Control transfers succeed on a recycled slot every time, so it only ever shows
on the periodic endpoint.

The mechanism is not identified. `CTXDUMP` confirmed the controller holds the right
route, speed, TT slot, TT port, interval and Max ESIT Payload for both devices, and hype
re-zeroes the device context and EP0 ring on Address Device. So this build **tests the
correlation** rather than asserting a cause: the hub walk now keeps a bounded number of
non-HID slots (3 of a pool of 8 per controller) instead of handing them straight back, so
no claimed HID inherits one.

## The freezes are fixed

Those were mine. Eight halt recoveries between t=51.6s and t=55.2s -- 3.6 seconds of
three synchronous xHCI commands each, run from the guest dispatch loop. Stop Endpoint is
gone from that path (it returned `cc=19 Context State Error` all eight times; it is
defined on a *running* endpoint, not a halted one), consecutive recoveries drop 8 -> 2,
and the backoff goes 8192 -> 200000 polls. Worst case is now two commands twice, then a
long rest.
