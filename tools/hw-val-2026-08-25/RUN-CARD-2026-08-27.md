## What changed in the binaries since the 09:14 boot

`#734`: the two claimed HIDs shared ONE interrupt-IN ring, report buffer and
"transfer outstanding" flag per controller. That flag gates arming, so an idle
input device held it forever and the other endpoint's doorbell was never rung
again -- which is why the keyboard AND the mouse both read `reports=0`. Each
endpoint now owns its own block. `tools/734/run-734-qemu.sh` reproduces the
lock-out in QEMU (keyboard frozen at 67 reports across 100 keystrokes pre-fix,
120 -> 320 with the fix).

A failed report transfer now also names its completion code:
`host-xhci: interrupt-IN transfer FAILED slot=N ep=N trb=0x... cc=N [#734]`.
The 09:14 boot's `errors=1` was one keyboard transfer failing with a code the log
could not name, and it stayed at 1 only because the endpoint never re-armed.

Three things are physical and only you can do them:

1. Leave the **keyboard and mouse on the USB 2.0 hub**. Moving them to a root
   port is the fallback experiment for #734, not this boot.
2. **Plug something into one of the two SuperSpeed hubs** on controller 2 ports 7

   so #739's "their devices are listed" half proved nothing.
3. **Type on the keyboard and DO NOT touch the mouse** for a while, then also
   move the mouse. That order is the fix's own test: pre-fix, an idle mouse
   silenced the keyboard permanently.
