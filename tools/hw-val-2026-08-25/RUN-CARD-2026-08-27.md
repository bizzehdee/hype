## READ THIS FIRST -- #735 is CLOSED, and this boot is confirmation

The root cause was in boot 6's own log, under a counter nobody had read:

```
APVCPU vm0/1: exits=53888372 unhandled=37009095 last=0x400@0xffffffffc08a7043
```

37 million unhandled nested page faults on vCPU 1 -- the vCPU the reboot was pinned to --
because the AP dispatch loop counted an NPF that no device claimed and re-entered with RIP
unchanged. `vmm_absorb_mmio_npf()` (all-ones read, dropped write, RIP advanced) has existed
since GLADDER-1 and the BSP loop always called it; the AP loop never did.

Fixed and **proven on the AP path in QEMU** by a new SMP microtest that brings up vCPU 1
and has it touch an unclaimed address: `unhandled=0 unclaimed=2`. #735 and #749 are closed.

**One correction to every earlier log.** "NPF at gpa 0x100000004" in all five hardware logs
is NOT an address -- the message printed the NPF error code (EXITINFO1, bit 32 = "a guest
physical address caused this") under a label saying address. The real GPA was never
recorded. Fixed; it now prints both, labelled.

So this boot confirms a proven fix rather than testing an unproven one.

### Why this boot exists

Five hardware boots have reproduced #735 and **not one contains a single kernel message.**
Alpine's live-ISO cmdline sends kernel output to tty0 and the serial prompts come from
inittab, so `\RUN1A.LOG` ends at the shell prompt after `reboot` and says nothing about what
the kernel did next. That silence has been read as "the guest wedged immediately"; it is
equally consistent with a kernel getting most of the way through a shutdown it could not
report. The logs cannot tell those apart, and everything else about #735 depends on which
it is.

`dmesg -w` does not care what `console=` says. This script backgrounds it onto `/dev/ttyS0`
before rebooting, plus a one-second heartbeat, both under `setsid` so init killing the
shell's process group does not take them with it.

### What to read, and what each answer means

```
LC_ALL=C grep -a 'HB-\|DMESG-STREAMING\|reboot:\|Restarting' \RUN1A.LOG | tail -40
```

| what the tail shows | what it means |
|---|---|
| `HB-` ticks stop, no further kernel lines | userspace died first -- the wedge is init or the shell's own group, before the kernel's reboot path |
| `HB-` ticks stop but kernel lines KEEP COMING | the kernel is alive and past userspace. That is where the `0xfb` CALL_FUNCTION_SINGLE storm lives, and the last kernel line names the function that hung |
| both keep going forever | nothing is wedged and the reboot request itself never took -- a different bug from the one assumed |
| a second `localhost login:` | #735 did not reproduce this boot. Say so; it has been 5/5 until now, and the intervening `#748` fix is the obvious suspect |

**Expect a TIMEOUT, not a PASS.** The script ends in an `expect` that will not be satisfied
if #735 reproduces. That is intended -- the evidence is the log, not the verdict. Let it run
its 15 minutes, or power off two minutes after the heartbeat stops.
