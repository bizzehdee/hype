### Run A -- keyboard and mouse where they are now, on the 2.0 hub

Nothing to change physically. Type on the keyboard and move the mouse.

**Before the CTXDUMP, one 5-second physical check.** The Keychron `3434:0da4` has a
side switch (Cable / Off / Bluetooth). In wireless mode the USB side still enumerates
and answers control transfers, which is all hype has proven it can do with this device.
Make sure it is set to cable/USB, and that it is not simultaneously paired and awake on
Bluetooth.

Two lines matter now. First, what hype parsed and picked:

```
LC_ALL=C grep -a 'cfg .* bytes' \HYPE.LOG
```

```
host-hid: keyboard 3434:0da4 cfg N bytes -- picked iface=? ep=0x81 mps=8 interval=1 cfgval=?
```

`TRUNCATED` in that line means the config descriptor filled hype's 256-byte buffer and
the interface walk may have bound to the wrong endpoint -- the ctrl2 port-1 device on
this host already reads `cfg 256 bytes`, so the cap is reachable here. The Keychron has
three interrupt-IN endpoints (0x81 mps=8, 0x82 and 0x83 mps=32); this line is how to
tell "hype picked 0x81" from "0x81 is the one the boot interface reports on".

Second, the CTXDUMP pair. Read them side by side:

```
LC_ALL=C grep -a CTXDUMP \HYPE.LOG
```

Expect four lines: `int-in` + `its-TT-hub` for the keyboard (slot3), and the same for
the mouse (slot4). The keyboard's and the mouse's `int-in` lines should differ ONLY in
`route`, `mps` and `esit`. Any other field that differs -- `speed`, `ttslot`, `ttport`,
`ttt`, `interval`, `state`, `cerr`, `maxburst`, `mult` -- is the bug, in one line.
