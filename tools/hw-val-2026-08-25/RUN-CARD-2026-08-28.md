# Boot 8 -- USB hot-plug, and a #750 soak

This boot replaces the staged boot 7. Boot 7 was a **#735 diagnostic**, and #735 has since
been closed and proven in QEMU by a new SMP microtest, so that boot no longer has a question
to answer. Nothing was lost -- boot 7 was never run.

## DO NOT UNPLUG THE HYPE DRIVE

The 476 GB stick labelled `HYPEBOOT` is the boot medium **and** the log medium. Pulling it
ends the run and destroys the evidence. Only the keyboard and the mouse move in this
sequence. Nothing else.

## What changed since boot 7 was staged

| # | what happened |
|---|---|
| 735 | **CLOSED.** The AP dispatch loop never called `vmm_absorb_mmio_npf()`, so an unclaimed NPF re-entered with RIP unchanged -- 37M of them on the pinned vCPU. Proven on the AP path in QEMU |
| 749 | **CLOSED.** The same fault, as its own ticket |
| 751 | **CLOSED.** The first SMP microtest: brings up a guest AP and runs test code on it. This is what proved #735 |
| 752 | **CLOSED.** `hype_mmio_decode()` could not decode the moffs MOV forms (A0-A3). Found by that microtest -- the AP spanned one 11.6M times |
| 750 | **CLOSED, and this boot is its hardware exposure.** See below |
| 747 | Built and QEMU-proven; its hardware half is **not** in this boot (it needs a second, sanctioned scratch USB device) |
| 753 | **NEW.** The deferral metric that nearly sent #750 the wrong way is itself wrong. Not in this boot |

## #750, and why an idle guest is the test

`hype_svm_can_accept_interrupt()` refuses while the STI shadow is set, regardless of IF, and
the only thing that cleared the shadow was `wake_hlt()` -- which #641 had correctly made
conditional on an injection having happened. That closes a loop:

    shadow set -> nothing can be injected -> wake_hlt never runs -> shadow stays set

An AP that entered it stopped taking interrupts permanently. Linux idles at `sti; hlt`, so an
idle AP is exactly where it happens. The fix clears the shadow at the AP loop's HLT exit: the
HLT *is* the shadowed instruction, and a HLT exit means it executed, so the shadow is spent.

Reproduction was about 1 in 3 before the fix and 0 in 11 after it (p ~= 1.2% by chance). That
is QEMU. **This boot is the first time it runs on real SVM**, and the twenty idle minutes
while you handle the cables are the point -- the bug needs an AP to go idle and stay idle.

You do not have to do anything for this half. Just do not give the guest work.

## Before you start

- Keyboard and mouse on the **2.0 hub**, where they are now. Do not re-cable yet.
- Boot the drive. `\EFI\BOOT\BOOTX64.EFI` is the default build; `\hype.cfg` is `hype1a.cfg`.
- Wait for the guest to print `OPERATOR-GO` on the screen. Nothing before that counts.

## The sequence

Wait the stated time at each step. The waits are not padding: hype polls the hub's
status-change endpoint on its own schedule, and a port that changes twice inside one poll
interval is one event, not two -- which would test nothing.

| step | do this | wait | what it proves |
|------|---------|------|----------------|
| A | Unplug the **mouse** from the hub | 15 s | #746 -- a departure *behind a hub* is seen at all. The hub's status-change endpoint is the only way hype can learn this |
| B | Plug the mouse back into the **same hub port** | 15 s, then move the mouse | #745 + #746 -- re-enumerated and re-claimed behind a hub |
| C | Unplug the **keyboard** from the hub | 15 s | #744 -- departure teardown: the slot is released, and the **mouse must keep working**. Move the mouse to check |
| D | Plug the keyboard back into the **same hub port** | 15 s, then **press Right-Ctrl + Right-Alt + D** | #745 -- claimed again *and* the chord path survived the re-claim. This is the exact thing that did not work on boot 6 |
| E | Move the keyboard to the **front USB-C** port (direct to the motherboard) | 15 s, then chord again | #744 -- the same on a **root port**, which is a different code path from the hub one |
| F | Move the keyboard back to the hub | 15 s, then chord again | Both directions, and no state left over from E |
| G | **Stop touching it.** Let it sit | until the run ends | #750. The guest must be idle. Do not type into it |

The run ends by itself, on a timeout, after about 20 minutes from login. **A timeout is the
expected ending, not a failure.** There is no `pass` line in this script -- the evidence is
the log, not a verdict.

## What a good run looks like

In `\HYPE.LOG`, one line per step, from `boot/main.c`:

```
host-hid: mouse behind hub slot N port M DEPARTED -- releasing ...
host-usb: hub slot N port M ARRIVED -- 046d:c547 slotK speed... 
host-hid: keyboard 3434:0da4 on port M slotK DEPARTED -- releasing ...
```

and `DIAG: HUBPOLL hubs=1 polls=... reports=...` with **reports non-zero**. QEMU has never
produced a non-zero `reports` -- it does not model the hub's status-change endpoint -- so
this line is the entire reason #746 needs hardware.

In `\RUN1A.LOG`: `HB-` ticks every 10 s with **no gap**, and no `soft lockup`.

## What a bad run looks like, and what it would mean

- **A step produces no line at all** -- the change was never noticed. For a hub step that is
  #746 (status-change endpoint); for the USB-C step it is #744 (port change events).
- **`ARRIVED` but the chord does nothing at step D** -- claimed but not wired into the input
  path. That is #745, and it is the boot-6 symptom recurring.
- **The mouse dies at step C** -- teardown released more than the departing device's own
  slot. That is #744 and it is the worse outcome, because it means a shared structure.
- **`soft lockup` in `\RUN1A.LOG`** -- #750 is not fixed on hardware. Do not re-stage; the
  log is the evidence. Note which CPU the watchdog names.
- **`HB-` gaps but no lockup line** -- something stalled the whole guest rather than one AP.
  That is not #750; it would be new.

## Afterwards

Archive both logs before the drive is re-staged -- `stage.sh` refuses to run while they are
non-empty, deliberately, so a boot's evidence cannot be lost to a re-stage:

    cp \HYPE.LOG \RUN1A.LOG  tools/hw-val-2026-08-25/logs/boot-8/

`\HYPE.LOG` needs `LC_ALL=C grep -a` -- on-stick logs contain invalid UTF-8 and a plain grep
matches nothing.
